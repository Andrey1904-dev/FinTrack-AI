# FinTrack-AI — аудит перед доработкой

**Дата:** 2026-10-03  
**Область:** текущая рабочая ветка; `src/`, все миграции Supabase, Edge Functions и общий код Telegram, hooks/data services, расчёты, тесты, RLS, PWA и GitHub Actions.

## Итог

Это не пустой стартовый проект: Personal OS уже содержит рабочие экраны и значительную часть повседневных сценариев. Существующие модули нужно расширять, а не дублировать. Наиболее ценные следующие шаги — сделать Dashboard прогнозным и честно показывать ограниченность исходных данных, привести месячный бюджет к план/факт, исправить целостность операций автомобиля и сократить чтение всей истории на экранах, которым она не нужна.

Полный Net Worth, универсальная доступность покупок, документы, веб-аудит-лог/undo, AI и car-vs-new сценарий отсутствуют либо являются только заготовками; это не следует считать готовыми функциями.

## Метод проверки и ограничения

- Просмотрены все исходники `src/`: приложение и маршруты, страницы/формы, auth, data hooks, UI, расчёты, стили и тесты.
- Просмотрены три SQL-миграции, схема таблиц и политики, RPC и зависимости legacy-полей, читаемых Telegram-ботом.
- Просмотрены все Supabase Edge Functions и `_shared`-модули, тест Telegram, настройки PWA, README и workflow деплоя.
- В этом окружении нет безопасного подключения к production Supabase для чтения живой схемы, данных или создания production backup. Выводы по базе относятся к миграциям репозитория и PGlite-тесту; перед применением любых будущих миграций на живой базе нужен отдельный backup/restore check.
- После `npm ci` исходные проверки прошли: `npm run lint`, `npm run typecheck`, `npm test` (65 тестов вместе с Telegram checks), `npm run test:db`, `npm run build`.
- `npm audit` выявляет **9** уязвимостей (4 moderate, 5 high): production-зависимость `react-router-dom`/`react-router` попадает под advisories до 7.18.0; остальные выявленные advisories относятся к цепочке разработки (включая Tailwind 3 и Vitest). Автоматическое исправление предлагает major upgrades; их нельзя делать механически без отдельной проверки совместимости.

## Implemented

- **Приложение и auth:** React 18 + TypeScript + Vite, lazy routes, HashRouter (GitHub Pages), Supabase Auth с PKCE, восстановление пароля, переключение аккаунтов с очисткой query-cache, error boundary.
- **Финансовый ledger:** доходы/расходы в `finance_operations`, категории, фильтрация и поиск в разделе, месячная сводка/графики, CSV и JSON export, быстрые формы. Категорийные месячные лимиты хранятся в `finance_profiles.budgets` и совместимы с Telegram.
- **Повторяющиеся операции:** отдельные повторяющиеся доходы/платежи, периодичность, планирование ближайших дат и отметка «оплачено» с записью операции.
- **Долги:** кредиты/карты/прочие долги, история, атомарный RPC для платежа, связанный расход, лавинный расчёт закрытия и CSV.
- **Автомобиль:** несколько автомобилей, текущий автомобиль, заправки, сервис/ремонт, прочие расходы, напоминания по дате/пробегу, топливная статистика, выборочный TCO-калькулятор и сохранение/сравнение сценариев.
- **Другие разделы:** цели, повторяющиеся задачи, обучение/темы, заметки с тегами/закреплением, список IT-команд и копирование.
- **Today/Dashboard:** экран «Сегодня», сводка месяца, быстрые действия, настраиваемые блоки главной и ближайшие финансовые/автомобильные сигналы.
- **Поиск и уведомления:** Ctrl/Cmd+K, поиск по операциям, долгам, авто, сервису, заметкам, задачам, целям и командам; производные уведомления и опциональные browser notifications.
- **Telegram:** webhook, привязка одноразовым кодом, проверка Telegram secret header, service-role доступ только в Edge Functions, дедупликация/rate limit, preview → подтверждение операции, отчёты, лимиты, цели, долги/платежи, настройки уведомлений, расписание уведомлений и 24-часовой `/undo` для операций, созданных через Telegram.
- **База и RLS:** три последовательные миграции; миграция Personal OS аддитивна, переносит прежний профиль с копией в `legacy_profile_backup`, не удаляет основную финансовую таблицу. Таблицы Personal OS закрыты RLS, owner-политиками и проверками принадлежности дочерних строк родителю. Telegram state из браузера закрыт; критичные RPC выданы только service role.
- **PWA / CI:** install manifest и иконки, auto-update service worker с precache статических ресурсов; GitHub Actions запускает lint/typecheck/tests/db tests/build и публикует Pages из `main`.

## Partially implemented

- **Dashboard 2.0:** есть приветствие, текущие доходы/расходы/свободный поток, общий долг, быстрые действия, авто- и задачные блоки. Нет текущего ликвидного баланса, активов, обязательств вместе, Net Worth, безопасного остатка и расчётного баланса на ближайшие даты. Предстоящий список строится примерно на месяц, а не показывает компактный 7–14-дневный cash-flow.
- **Cash Flow:** `buildEvents` объединяет часть будущих доходов/регулярных платежей, минимальные платежи долгов, автомобильные напоминания и дедлайны целей. Вкладка «Прогноз» показывает оценку свободного потока и закрытия долгов по месячным средним, но не строит ежедневный ряд «дата → прогнозируемый баланс» и не использует исходный баланс, цели/покупки/прогноз авто как единый engine.
- **Budget:** есть лимиты категорий с фактом и процентом выполнения, общие для приложения и Telegram. Отдельного месячного плана ожидаемого дохода, обязательных расходов, выплат долга и накоплений нет.
- **Financial calendar:** календарь показывает регулярные платежи/доходы, приближённые платежи долгов, датированные автомобильные напоминания и дедлайны целей. В нём нет фактических операций, задач/пользовательских событий, подписок как отдельного типа и баланса после выбранной даты.
- **Affordability / What-if:** What-if позволяет оценить автокредит, ежемесячный остаток и влияние первоначального взноса на накопления. Это не универсальный калькулятор покупки по цене и дате, не связан с прогнозом денежных средств и не даёт рекомендованную дату.
- **Автомобиль / TCO:** уже рассчитываются топливо, сервис, прочие расходы, месячная стоимость и топливная стоимость километра; калькулятор включает кредит, топливо, страховку, налог и резерв обслуживания/ремонта. В форме автомобиля нет марки/модели как отдельных полей, VIN/регномера/фото/цены покупки/текущей стоимости; в реальном TCO не учитываются амортизация и кредит текущего автомобиля.
- **Сравнение авто:** можно сравнить сохранённые потенциальные сценарии, без автоматического выбора победителя. Нет текущего автомобиля как baseline для «оставить vs купить», а разница не представлена как надёжное сравнение совокупных расходов за одинаковый срок.
- **Smart Input:** детерминированно распознаются сумма, часть категорий и некоторые доходы (`+1200 бензин`, `зарплата 150к`); форма показывает распознанные поля до сохранения. Нет надёжного разбора всех заявленных команд, предупреждения об неоднозначности/уверенности, привязки к долгам/покупкам и полноценного мобильного подтверждения-предпросмотра.
- **Telegram 2.0:** уже поддерживаются `/today`, `/balance`, `/goals`, а `/debts` является alias команды `/credits`; операции всегда подтверждаются preview-кнопкой. Отдельной сводки автомобиля/команд `/cars`, `summary`, фразы «что у меня завтра?» и полноценного ввода погашения долга нет.
- **Monthly reports:** месячные операции и сравнение периода есть в Telegram; веб показывает месячные графики/статистику. Нет формируемого месячного отчёта с отдельными блоками сбережений, долга, авто и сравнением двух полных месяцев.
- **Mobile/PWA:** уже есть адаптивный layout, FAB, safe-area, install manifest и offline precache. Нет явного offline fallback с полезным состоянием данных и локальной очереди; надпись о сохранении формы не означает, что черновик переживёт закрытие/перезагрузку. Текущая нижняя навигация — Главная/Финансы/Авто/Задачи/Ещё; «Today» спрятан в «Ещё».

## Broken

- **Dashboard читает больше истории, чем нужно.** `useRows` загружает страницы до 50 000 строк. `useOverview` вызывается и на Dashboard/Today/уведомлениях и получает весь `finance_operations`; car-блоки также читают полный журнал, хотя главной нужны месяцы/последний год. Глобальный поиск аналогично загружает несколько полных таблиц. Это нарушает требование не загружать всю базу на Dashboard и будет ухудшаться с ростом данных.
- **Авто-операция и финансовый ledger могут расходиться при редактировании.** `RefuelForm`, `ServiceForm` и `CarExpenseForm` создают связанную операцию при добавлении, но edit-flow не обновляет уже связанную строку `finance_operations`; чекбокс учёта скрыт при редактировании. В результате пользователь может видеть новую сумму/дату в авто-журнале и старую — в финансах. Проверки результата отката/обновления пробега также местами игнорируются.
- **`finance_operations.recurrence` не является расписанием.** Форма дохода принимает weekly/monthly/yearly, но будущие события строятся из `recurring_payments`; recurrence у операции не порождает платежи календаря и не должна считаться прогнозом регулярного дохода.
- **Команда умного ввода о погашении кредита не реализована как платёж долга.** Например `+30000 погашение кредита` сводится к обычной expense-категории «Кредиты» и не меняет остаток долга/историю; UI должен явно предупреждать/маршрутизировать такую команду, чтобы ledger и долг не расходились.
- **Повторяющиеся задачи не гарантируют атомарность.** При отметке recurrent task сначала закрывается исходная строка, затем отдельным запросом создаётся следующая; при частичной ошибке задача остаётся закрытой без следующего повторения.
- **Недостоверная доступность данных для решений:** пользовательский интерфейс не показывает, что «свободно за месяц» — это доходы минус расходы, а не банковский баланс/ликвидные средства. Использовать это число как ответ «сколько можно потратить» некорректно.

## Missing

- Ручной стартовый cash balance/счета с остатками, безопасный минимум и сценарный прогноз баланса.
- Полный Net Worth: явные активы, обязательства, динамика и корректное различение ликвидных денег, накоплений и оценочной стоимости машины.
- Полноценный месячный план/факт поверх существующих категорийных лимитов; подписки как отдельная сущность/сводка.
- Универсальный «можно ли позволить покупку?» на заданную дату, влияние на резерв/цели/долги и рекомендуемая дата.
- Автомобильные поля по ТЗ (фото, VIN, регистрация, дата/цена покупки, оценка), амортизация, полный TCO текущего авто и сравнение текущего vs потенциального автомобиля.
- Детектор аномалий и месячная аналитика отклонений по категориям.
- Supabase Storage, привязанные к сущностям чеки/договоры/страховки/документы/фото.
- Audit log создания/изменения/удаления и короткий веб Undo для удаления.
- AI Edge Function и работа с реальными пользовательскими данными; в Settings сейчас только карточка «скоро». Нет отдельного action-preview/confirmation flow AI.
- Полный mobile navigation по целевому набору и доступный offline fallback/надёжная очередь.
- RPC/агрегированные серверные запросы для больших журналов и тесты производительности на больших выборках.

## Needs redesign

1. **Сначала общий расчётный контракт.** Развести значения «текущий баланс» (вводится/импортируется), «свободный денежный поток» (доход − расход), «долг», «активы», «обязательства» и «Net Worth». Не подменять одно другим.
2. **Cash Flow как единый детерминированный engine.** Общий нормализованный список future cash events с источником, датой, signed amount и правилами просрочки; дневные точки до 24 месяцев; пояснение допущений для долга, цели, автомобиля и покупок; unit tests.
3. **Хранение бюджета/настроек.** Существующую `finance_profiles.budgets` оставить совместимой с ботом. Новые настройки планов и safe balance хранить отдельно/аддитивно, с owner-RLS; не переопределять legacy JSON поля, читаемые ботом.
4. **Малые выборки.** Dashboard получает агрегаты/короткие диапазоны, экраны истории — пагинацию, глобальный поиск — запрос по конкретному тексту/индексу и ограниченное число результатов. Не менять семантику экспорта.
5. **Транзакционная связь авто ↔ ledger.** Добавление/изменение/удаление связанного автомобильного расхода должно атомарно обновлять соответствующую запись финансового ledger или RPC; определить единственный source of truth и исключить двойной учёт.
6. **Additive data migration discipline.** Перед применением на production — реальный backup и проверка restore, schema diff, отдельные тесты RLS/parent ownership/Telegram projection. Ни один новый экран не должен напрямую менять данные старых таблиц бота без тестов.
7. **Security/production:** отдельно обновить/проверить React Router и уязвимые dev-зависимости, оценить риск GitHub Pages + публичного Supabase publishable key только совместно с RLS, а для Storage добавить private buckets, path ownership, MIME/size allowlist и signed URLs.
8. **Продуктовый UX:** мобильная навигация Главная/Финансы/Авто/Today/Ещё, простой ввод по умолчанию и скрытые Advanced поля; не добавлять отдельный экран, если действие можно встроить в уже существующий финансовый/автомобильный поток.

## Реализация после аудита (локальная ветка, 2026-10-03)

- `useRows` теперь поддерживает серверные диапазоны дат и ограничение выдачи. Dashboard/Today берут операции за последние 6 месяцев; автомобильная сводка Dashboard ограничивает расходы 90 днями, а Cash Flow — автоисторию последним годом. Экспорт и полноценные страницы истории не урезались.
- Добавлен детерминированный `buildCashFlowForecast`: дневной ряд до 730 дней, signed события повторяющихся платежей/доходов, минимальных платежей долга с частичным первым периодом процентов, взносов к целям, покупок (API расчёта) и прозрачной оценки расходов текущего автомобиля. Расчёт различает исходный вручную введённый баланс, безопасный минимум, дефицит и отсутствие порога; покрыт unit-тестами.
- Finance → «Прогноз» получил форму исходного остатка/безопасного минимума, горизонты, дневной график и пояснение допущений. На Dashboard и «Сегодня» добавлены короткие сводки прогноза. Свободный месячный поток не трактуется как баланс.
- Добавлен текущий месячный план/факт (доходы, расходы без долгов/накоплений, долг, накопления). Настройки сохраняются в существующем owner-scoped `profiles.settings`, а прежние `finance_profiles.budgets` и Telegram-лимиты не меняются. Фактические накопления определяются явными расходными операциями категории «Накопления»; долг берётся из записей платежей и несвязанных расходов категории «Кредиты», связанные операции не считаются дважды.
- Добавлена аддитивная миграция `202610030001_sync_car_finance_operations.sql`: PostgreSQL-триггеры синхронизируют редактирование записи авто с её связанной финансовой операцией в той же транзакции и отклоняют cross-user ссылки через RLS. Удаление автомобильной строки по-прежнему сохраняет независимую финансовую историю; UI это сообщает.
- Новых таблиц не добавлено. Синхронизация автомобильных записей зависит от применения новой миграции: **на production она не применялась**, т.к. нет безопасного подключения и подтверждённого backup/restore. Сначала требуется обычный для проекта backup/проверка схемы, затем применение миграции; PGlite проверяет её локально и повторно.
- Текущие проверки: `npm run lint`, `npm run typecheck`, `npm test` (76 unit/smoke тестов + Telegram checks), `npm run test:db` и `npm run build` прошли. Остались предупреждения React Router Future Flags в тестах и существующее предупреждение Vite о двойном (static/dynamic) импорте `SearchDialog`.

### Остаток дорожной карты

Ручной баланс и месячный план/факт появились, но пока нет полного Net Worth, универсального affordability по покупке/дате, UI планирования будущей покупки, амортизации/расширенного TCO и сравнения с текущим авто, подписок/аномалий, Storage-документов, веб audit log/undo и AI Edge Function. Глобальный поиск и экраны истории всё ещё требуют серверного поиска/пагинации; миграцию выше нужно безопасно применить отдельно от GitHub Pages-деплоя.
